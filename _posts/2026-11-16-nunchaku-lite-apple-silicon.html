The same 4-bit SVDQuant checkpoints that run on CUDA now run on an M5 Mac, through PyTorch MPS (Diffusers) and MLX (mflux). New Metal kernels run the 4-bit layers as int8 matrix multiplies on the GPU's Neural Accelerators. All numbers come from an M5 with 24 GB, generating at 1024².

Two runtimes

Nunchaku Lite loads Nunchaku SVDQuant checkpoints into existing pipelines instead of shipping its own. On a Mac there are two pipeline ecosystems, so there are two runtimes.

Both read the same checkpoints, including the lite-infer repos with a runtime manifest and older lite checkpoints that list their quantized layers in config.json.

FLUX.1-dev, FLUX.2 Klein 4B and 9B, Z-Image Turbo and Qwen-Image Lightning run end to end on both runtimes, from the original Nunchaku checkpoints as well as the lite ones. A Nunchaku checkpoint holds the whole transformer, so the MLX loader builds an empty one and fills it from the checkpoint; the base model's transformer is never downloaded, which saves 23 GB for Z-Image Turbo and 38 GB for Qwen-Image.

How the 4-bit layers run on M5

The M5 Neural Accelerators

Every GPU core in the M5 has a Neural Accelerator, a unit built for matrix multiplication. Metal 4 shaders drive it through tensor operations (matmul2d in Metal Performance Primitives); earlier Apple GPUs run matrix multiplies on the ordinary shader cores. The accelerators are at their fastest with integers. Peak throughput of a bare matrix multiply on the M5:

operands (accumulator)throughput ↑
int8 × int8 (int32)~30 TOPS
int8 × int4 (int32)~30 TOPS
fp16 or bf16 × anything~15 TFLOPS

Two consequences shape the design. Int8 is twice as fast as bf16, so a layer gains by running its matmul in int8. And a 4-bit operand runs no faster than an 8-bit one (int8 × int4 matches int8 × int8), so 4-bit activations would add error without adding speed. So the layers run as W4A8 (4-bit weights, int8 activations) or W8A8 (the same 4-bit values stored expanded to int8), not as Nunchaku's CUDA W4A4.

The fused kernels come close to that ceiling. Here they are against a bf16 matmul at the projection shapes of a FLUX block for a 1024² image (4,608 tokens), with the scales, bias and low-rank branch all inside the int8 kernels:

projection (K → N)bf16 matmulW8A8 kernelW4A8 kernel
QKV 3072 → 921616.6 ms · 15.7 T9.1 ms · 28.6 T11.6 ms · 22.4 T
MLP in 3072 → 1228822.0 ms · 15.8 T12.1 ms · 28.8 T15.5 ms · 22.5 T
MLP out 12288 → 307232.1 ms · 10.8 T12.7 ms · 27.5 T17.0 ms · 20.4 T
attention out 3072 → 30725.7 ms · 15.3 T3.2 ms · 27.2 T4.0 ms · 21.5 T

T is trillions of operations per second, with a multiply-add counted as two. The W4A8 kernel is slower than W8A8 because it expands each 4-bit weight to its int8 value in the shader before the accelerator sees it. As whole layers, with activation quantization included, the four projections of a FLUX block take 47.2 ms with int8 and 58.4 ms with int4, against 81.5 ms in bf16: 1.73× and 1.40× faster. MLX's own 4-bit format, which mflux q4 uses, takes 78.1 ms: it stores 4-bit weights but does its arithmetic in bf16, so it saves memory but not time.

SVDQuant layers on the accelerators

An SVDQuant layer splits each weight into a small low-rank branch kept in 16-bit and a 4-bit residual with one scale per 64 input channels. On CUDA, the residual runs as a 4-bit × 4-bit matmul. Apple GPUs have no 4-bit matmul, but the M5's Neural Accelerators run int8 matmuls, reachable from Metal 4 shaders.

  • Activations are smoothed and quantized to int8 per token, a finer grid than the 4-bit activations the CUDA kernel uses.
  • Weights keep their 4-bit values. Each per-group scale is split into a per-channel scale and an integer-domain multiplier, so the int32 accumulator can run over the whole input dimension in one pass.
  • The epilogue applies the activation and channel scales, the bias, and the low-rank branch once, in the same kernel.

Two weight backends share that kernel. int8 stores the weights pre-expanded to int8, twice the memory of int4, and is the fastest. int4 keeps them 4-bit and expands them inside the kernel, about 20% slower per layer. backend="auto" picks int8 when the model fits in half of the GPU's memory budget, otherwise int4. On a 24 GB Mac that means int8 for Klein 4B and int4 for Klein 9B and FLUX.1-dev. Macs without Neural Accelerators fall back to a dequantized path.

The AdaNorm modulation layers are AWQ W4A16. On MLX they map losslessly onto MLX's own 4-bit format and its built-in kernel; on PyTorch MPS they use PyTorch's int4 matmul for MPS.

Attention

With the projections running in int8, attention and the small operations around it become a large share of each step. Two changes keep them on the accelerators as well.

Before attention, FLUX.1, FLUX.2, Qwen-Image and Z-Image all normalize each head of the queries and keys (RMSNorm) and apply rotary position embeddings. Both runtimes ran this as a chain of float32 elementwise operations with reshapes in between, which costs about as much as attention itself on Klein. It is now a single kernel that reads q, k and v straight out of the projection's output and writes them in the layout attention expects, for all four families. The same kernel source is built by MLX and by PyTorch. On PyTorch MPS it takes FLUX.1-dev from 6.37 to 5.24 s per step.

Attention itself runs fast on MLX: its built-in kernel uses the Neural Accelerators and reaches about 13 TFLOPS of the 15 available in bf16. PyTorch's attention on MPS runs at about 3.5 TFLOPS on the M5. MLX's kernel source is MIT-licensed, so the PyTorch runtime compiles a copy of it at load time and calls it on PyTorch tensors, without MLX installed. At Klein's shape (24 heads, 4,608 tokens) one attention call goes from 74 ms to 20 ms, and its error against a float32 reference is about a third of PyTorch's.

Image editing

FLUX.2 Klein also edits images: the input image is encoded by the VAE and its tokens are appended to the output image's tokens, so the transformer attends to both. The same Nunchaku checkpoint loads into mflux's edit pipeline (Flux2KleinEdit) with no changes. Try it

MLX

# pip install "nunchaku-lite[mlx]" mflux
import mlx.core as mx
from mflux.models.common.config.model_config import ModelConfig
from mflux.models.flux2.variants import Flux2Klein
from nunchaku_lite.mlx import load_nunchaku_pipeline

mx.set_cache_limit(1 << 30)  # keep MLX's buffer cache from pushing a 24 GB Mac into swap
model = load_nunchaku_pipeline(
    "mflux-community/flux2-klein-9b-mflux-q4",  # text encoder, VAE, scheduler
    pipeline_cls=Flux2Klein,
    checkpoint="lite-infer/flux.2-klein-9b-nunchaku-lite-int4-r32",  # only transformer/ is downloaded
    backend="auto",  # int8 or int4 from available memory
    model_config=ModelConfig.flux2_klein_9b(),
)
image = model.generate_image(seed=42, prompt="A golden retriever mid-leap catching a frisbee",
                             num_inference_steps=4, height=1024, width=1024, guidance=1.0)
image.image.save("klein9b.png")

For editing, load the same checkpoint into mflux's edit pipeline and pass the input image:

from mflux.models.flux2.variants.edit.flux2_klein_edit import Flux2KleinEdit

model = load_nunchaku_pipeline(
    "mflux-community/flux2-klein-4b-mflux-q4",
    pipeline_cls=Flux2KleinEdit,
    checkpoint="lite-infer/flux.2-klein-4b-nunchaku-lite-int4-r32",
    backend="auto",
    model_config=ModelConfig.flux2_klein_4b(),
)
image = model.generate_image(seed=42, prompt="Change the text on the cardboard sign to say JAZZ NIGHT.",
                             image_paths=["musician.png"], num_inference_steps=4, height=1024, width=1024, guidance=1.0)
image.image.save("musician_edit.png")

PyTorch MPS

# pip install "nunchaku-lite[torch]"   # the Metal kernels download from the Hugging Face Hub on first use
import torch
from diffusers import Flux2KleinPipeline
from nunchaku_lite import load_nunchaku_pipeline

repo = "lite-infer/flux.2-klein-4b-nunchaku-lite-int4-r32"
pipe = load_nunchaku_pipeline(
    repo,
    pipeline_cls=Flux2KleinPipeline,
    checkpoint="lite-infer/flux.2-klein-4b-nunchaku-lite-int4-r32/transformer/diffusion_pytorch_model.safetensors",
    torch_dtype=torch.bfloat16,
    device="mps",
    backend="auto",
)
pipe.to("mps")
image = pipe("A golden retriever mid-leap catching a frisbee", num_inference_steps=4, guidance_scale=1.0).images[0]
image.save("klein4b.png")

Limitations and next steps

  • The int8 and int4 backends need an M5-class GPU (Neural Accelerators) and macOS 26. Earlier Apple GPUs use the dequantized fallback.
  • INT4 checkpoints only; NVFP4 is not supported on Apple silicon yet.
  • The prebuilt Metal kernels on the Hugging Face Hub cover PyTorch 2.10 to 2.15; other PyTorch versions need a local build of nunchaku-lite-kernels.
  • MLX adapters exist for FLUX.1, FLUX.2 Klein, Z-Image and Qwen-Image; other families can use the generic manifest adapter.
  • Qwen-Image's 20B transformer is about 12 GB at int4. With its 7B text encoder it needs more than 24 GB, so on a 24 GB Mac the first step of each image swaps. On MLX, mflux keeps the bf16 text encoder resident during denoising; freeing it after encoding is next.
  • Attention runs in bf16. Running its query-key product in int8, as SageAttention does on CUDA, would use the accelerators' faster integer path.
